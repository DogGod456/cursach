# Руководство по работе с субагентами

Владелец определяет результат и поручает работу. Координатор подбирает субагентов для исследования, планирования, реализации, тестирования, Git и ревью, следит за зависимостями и возвращает владельцу проверенный результат.

```text
AGENTS.md                 входная инструкция для координатора
agent-infra/
  README.md               руководство для владельца проекта
  git.md                  ветки, коммиты, приёмка и выпуск
  review.md               задание ревьюеру и порядок исправлений
  testing.md              выбор проверок и команды для Go
  SOURCES.md              происхождение и версии материалов
  skills/                 локальные инструкции и шаблоны
  licenses/               условия распространения
```

## Как поставить задачу

Например, «Добавь поиск по имени. При пустой строке показывай все записи. Заверши задачу в dev». В постановке достаточно обозначить наблюдаемое поведение, важные ограничения и требуемый результат. Координатор подбирает проверки под проект.

1. Для многошаговой задачи субагент готовит план. Новый независимый рецензент проверяет его до начала реализации. После исправлений план читает следующий новый рецензент.
2. Исполнитель работает в короткой ветке, например `feat/search-by-name` от `dev`. Добавляет реализацию и тесты на поиск и пустую строку. Субагент проверяет результат по [правилам тестирования](testing.md), а при работе с Go выбирает проверки соответствующего модуля.
3. В PR указывают исходную задачу, условия приёмки и результаты проверок. Новый независимый субагент изучает весь diff по [порядку ревью](review.md). Каждое замечание получает исправление или проверяемое обоснование. После разбора следующий независимый ревьюер снова проверяет полный результат. Слияние возможно после явного «замечаний нет» и успешных проверок проверенной версии.
4. Задачу сливают в `dev` через squash с подробным русским сообщением. Владелец получает SHA, результат проверки интеграции и сведения о том, что ещё предстоит сделать.

## Как выпустить принятую задачу

```text
dev → выбранный SHA → сборка и стенд test → preprod → приёмка → master → prod
```

Подготовка и выкладка выполняются по поручению на выпуск. Если во время проверки в `dev` вошло следующее изменение, предпрод получает ранее выбранный SHA. Предпрод и прод получают один и тот же проверенный артефакт. В коде на всех ветках хранятся тесты. В поставку включают файлы, нужные приложению во время работы. Для срочного исправления используют `hotfix/тема` от фактически работающей версии, проводят его через приёмку и возвращают исправление в разработку. Подробности, включая занятый предпрод и откат, приведены в [правилах Git](git.md).

## Как перенести комплект

Скопируйте в корень нового репозитория [AGENTS.md](../AGENTS.md) и каталог `agent-infra/` целиком. Если в целевом проекте уже есть свои инструкции, объедините точки входа и сохраните действующие проектные ограничения. Сверьте постоянные ветки, права публикации, команды сборки и условия доступа к стенду. Опишите особенности проекта рядом с его собственным кодом и дайте на них ссылку из его точки входа.

Для первого запуска достаточно дать координатору задачу и критерий готовности и проверить, что он нашёл локальные маршруты Git, тестирования и ревью. Исходники, версии, лицензии и условия применения сторонних инструкций собраны в [реестре материалов](SOURCES.md). Сами инструкции читаются с диска. Запуск тестов, CI, публикация и развёртывание требуют инструментов и доступов соответствующего проекта.
