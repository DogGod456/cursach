# Проверки и тесты

Субагент-исполнитель начинает с критерия приёмки. Записывает входные условия, действие и наблюдаемый результат. Команды, версии зависимостей и способ поднять стенд берёт из проекта. Тесты и фикстуры хранятся рядом с версией исходников, к которой относятся.

## Как выбрать проверку

| Изменение | Доказательство |
|---|---|
| Исправление дефекта | Воспроизвести исходный симптом тестом. Увидеть ожидаемое падение, внести исправление и повторить тот же запуск. |
| Новая функция | Зафиксировать требуемый результат через публичную точку входа. Проверить основной сценарий и существенный для задачи отказ. |
| Рефакторинг | Проверить существующее правильное поведение до изменения и повторить те же проверки после. Для данных прошлых версий использовать совместимую фикстуру. |
| Изменение прав или миграции | Поднять временную БД нужной версии. Проверить запрос под рабочей ролью, обновление существующей схемы и повторный запуск. |
| Изменение пользовательского сценария | На изолированном стенде пройти затронутый путь клиента. Проверить внешний результат, в том числе после переподключения или повтора, если это часть задачи. |
| Документация, инструкции агентам | Открыть указанные относительные пути и пройти описанный сценарий от входной инструкции до результата. Проверить примеры на соответствие реальным командам и правилам. |

Методика написания тестов приведена в [test-driven-development](skills/test-driven-development/SKILL.md).

## Профиль Go

Запускать из корня соответствующего модуля. Для репозитория с несколькими модулями определить их границы по go.mod и go.work и проверить каждый затронутый модуль и зависимых потребителей. Версию Go брать из настроек проекта. Форматирование проверить через `gofmt -l` со списком изменённых Go-файлов; ожидаемый вывод пуст.

```sh
go build ./...
go vet ./...
go test -count=1 ./...
```

Для теста обработчика использовать реальный HTTP-маршрут и httptest. Для таблицы вариантов удобно использовать t.Run. Временные файлы создавать в t.TempDir(), ресурсы закрывать через t.Cleanup(). Для проверки goroutine, доступа к общей памяти и жизненного цикла соединений добавить конкурентный сценарий и запустить `go test -race -count=1 ./...` на поддерживаемом CI runner с нужным компилятором. Детектор исследует выполненные пути, поэтому тест должен действительно запускать пересекающиеся операции.

Явно включить integration- и E2E-наборы, если проект держит их под отдельными тегами или командами. В CI подготовить временные сервисы и данные, дождаться готовности и обеспечить очистку после любого исхода. В отчёте записать фактические команды, версию среды, SHA проверенной версии, коды завершения и пропуски. Вывод Go `[no test files]` подтверждает компиляцию пакета и указывает на отсутствие тестов. Проверку без нужной БД или браузера отметить как невыполненную.

Перед слиянием получить свежие результаты на итоговой версии. При проверке в CI различать SHA головы ветки и синтетического merge-коммита; сохранить оба, если использовались. После слияния проверить получившийся коммит и связать артефакт с ним. Правила проверки доказательств — [verification-before-completion](skills/verification-before-completion/SKILL.md).
